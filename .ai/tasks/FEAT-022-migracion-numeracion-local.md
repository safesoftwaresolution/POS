# FEAT-022 — Migración y entidades de numeración local + `company.id` por local

> Parte del plan "Alegra como proveedor de facturación". Solo backend.

## Objetivo
Crear el esquema y las entidades que Alegra necesita porque **nosotros** enviamos el consecutivo y la resolución: rangos locales, libro de asignaciones, `company.id` por local/entorno e identificador del documento en el proveedor.

## Depende de
Nada (puede ir en paralelo con FEAT-021).

## ⚠️ Número de migración
`.ai/features.json` reserva **V20** para **FEAT-019** (pending). Antes de crear el archivo, listar `backend/src/main/resources/db/migration/` y usar la **siguiente versión libre** (hoy V21 si FEAT-019 ya tomó V20; V20 si no). En este documento "V<N>" es esa versión. Nunca editar una migración aplicada.

## Context Pack (R8)
- Docs (4): `backend/docs/modules/billing/spec.md` (Modelo de Datos), `backend/docs/_database-schema.md`, `backend/docs/_conventions.md`, `backend/docs/_security.md`.
- Código (≤5): `billing/internal/entities/StoreBillingConfig.java`, `billing/internal/entities/ElectronicInvoice.java`, `billing/internal/entities/NumberingRangeAudit.java` (como referencia de estilo), `billing/internal/repositories/StoreBillingConfigRepository.java`, `billing/internal/controllers/StoreBillingConfigController.java`.
- Tests de referencia: `backend/src/test/java/com/sciencebot/pos/schema/V17MigrationSqlTest.java` (Flyway en H2 privada).

## Qué se construye
`V<N>__Alegra_Local_Numbering.sql` (**seguro en H2**: sin `CHECK … IN (…)`; validar enums en la aplicación; tipos que existan en H2 y PostgreSQL):
- `billing_numbering_range`: `id` identity, `store_id` (FK a `stores`), `environment` VARCHAR(12), `document` VARCHAR(2) (`01` factura, `91` nota crédito, `92` nota débito), `prefix` VARCHAR(4) NOT NULL, `resolution_number` VARCHAR(14) NULL, `min_number`, `max_number`, `next_number` BIGINT, `start_date`/`end_date` DATE NULL, `technical_key` VARCHAR(255) NULL, `active` BOOLEAN, `deleted` BOOLEAN, `created_at`/`updated_at`. Único `(store_id, environment, document, prefix, resolution_number)`; índice `(store_id, environment, document, active)`.
- `billing_document_number`: `id`, `store_id`, `environment`, `document`, `reference_code` VARCHAR(100), `range_id` (FK), `prefix`, `number` BIGINT, `idempotency_key` VARCHAR(36), `completed` BOOLEAN, timestamps. Únicos `(store_id, environment, document, reference_code)` y `(range_id, number)`.
- `ALTER store_billing_config`: `sandbox_company_id`, `production_company_id` VARCHAR(64) NULL.
- `ALTER electronic_invoices | electronic_credit_notes | electronic_debit_notes`: `provider_document_id` VARCHAR(64) NULL.

Código:
- Entidades package-private `NumberingRange` y `DocumentNumberAllocation` con repositorios (`findActiveForUpdate(storeId, env, document)` con `@Lock(PESSIMISTIC_WRITE)`, `findByStoreAndEnvAndDocumentAndReference`).
- `StoreBillingConfig`: campos `sandboxCompanyId`/`productionCompanyId` y `companyIdFor(env)`; setters con validación (no vacío).
- Entidades de factura/notas: campo `providerDocumentId` con getter y método de dominio para asignarlo una sola vez (`assignProviderDocumentId`).
- Endpoint `PUT /api/v1/backoffice/stores/{storeId}/billing/company-id?environment=` (solo `SUPER_ADMIN`) con body `{ "companyId": "..." }` en `StoreBillingConfigController` + `ApiDoc`; servicio `updateProviderCompanyId(storeId, env, companyId, actor)`; `BillingActivationDto` expone solo un booleano de "company id configurado" por entorno (nunca el valor si se considera sensible; el id de empresa no es secreto, pero seguir el criterio de `sandboxConfigured`).

## Criterios de aceptación
- [ ] `V<N>MigrationSqlTest` verde: columnas/tablas/únicos existen en una H2 privada; la migración corre sobre el esquema V1..V<N-1>.

- [ ] El endpoint exige `SUPER_ADMIN`, es idempotente y audita `updatedBy`.
- [ ] `.\mvnw.cmd test` en verde.
