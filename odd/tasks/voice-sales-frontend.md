## Specs
S1. **La voz prepara la venta; el cajero la confirma.** Dictating only fills the existing ticket. Until the cashier reviews it, **no se registra la venta, no se descuenta stock y no se solicita una factura a la DIAN**. The frontend never calls `POST /sales` from the dictation flow; the normal checkout does, with its own `Idempotency-Key`.
S2. Example: *«Dos cafés grandes y una botella de agua para Ana Pérez. Paga en efectivo con cincuenta mil»*. If there are two customers named Ana Pérez the review step shows both options. It never picks one and never silently replaces Ana with "Cliente General".
S3. **Dictar:** `POST /api/v1/voice-sales/preview`, raw binary body (no multipart, no URL, no `storeId`), `Content-Type` `audio/webm` or `audio/wav`, at most 5 MiB (5 242 880 bytes). Send it through `fetchApi` in `services/http.js` (it already lets `options.headers` override `Content-Type` and accepts a Blob body) from a new `services/voiceSalesApi.js`.
S4. **Revisar:** the response is `{ items:[{ item:Reference, quantity|null }], customer:Reference, paymentMethod:Reference, cashReceived|null, pendingFields:[...] }`. A `Reference` is `{ mention, status, candidates:[{ kind, id, code, label }] }` with `status` one of `RESOLVED`, `AMBIGUOUS`, `NEEDS_REVIEW`, `NOT_FOUND`, `NOT_PROVIDED`; `kind` one of `PRODUCT`, `SERVICE`, `CUSTOMER`, `PAYMENT_METHOD`. Absent amounts and quantities are `null`; a null is never "1", "Cliente General" or "efectivo". The cashier corrects the draft locally, with no further AI call.
S5. **Confirmar:** after review the draft is applied to the POS ticket (cart, customer, payment method, cash received) and the cashier charges through the existing `CheckoutModal` / `handleCompleteSale`, with the existing idempotency key and `sendElectronicInvoice` left to the cashier's own choice (`issueDian`, default false). Do not touch that flow.
S6. Errors from the endpoint arrive as `{ "message": ... }`: 403 role/store, 404 feature disabled on this server, 413 too large, 415 unsupported type, 429 quota, 503 provider unavailable. Manual sales always keep working; the dictation error never blocks the ticket.
S7. Privacy: audio is never persisted in the browser (no localStorage, sessionStorage, IndexedDB, object URLs kept after use, or files). The Blob is dropped after the request settles; microphone tracks are stopped when recording ends, errors or the component unmounts. The transcript is not returned by the backend and must not be logged. No `console.log` of the draft or the audio.
S8. Review rules (decided by the parent, assumptions A1-A6 below). Assumptions: A1 the draft is applied to the existing ticket, it does not open its own checkout. A2 recording is a toggle button (tap to start, tap to stop) with an automatic stop at 45 s; mime `audio/webm` through `MediaRecorder`; if the browser cannot record WebM the button explains it instead of failing. A3 `RESOLVED` items are pre-selected; `AMBIGUOUS` and `NEEDS_REVIEW` require choosing one candidate or dropping the line; `NOT_FOUND` can only be dropped (the cashier searches the catalog normally); a missing quantity must be typed by the cashier. A4 customer `NOT_PROVIDED` keeps the ticket's current customer, shown explicitly; `AMBIGUOUS`/`NEEDS_REVIEW` must choose a candidate or keep the current customer; same for payment method (only codes present in the active `PAYMENT_METHODS` list can be applied). A5 `cashReceived` pre-fills the cash field only when the chosen payment method is cash; the cashier can edit it. A6 stock: a dictated quantity above available stock is capped at the stock with a visible warning, and an item with no stock cannot be applied (same rule as `addToCart`). The Apply button stays disabled while any item is undecided.
S9. UI follows the existing frontend conventions in `CLAUDE.md` ("Frontend Architecture"): semantic Tailwind tokens (`bg-card`, `border-line`, `text-ink`...), shared `components/ui` (`Modal`, `Button`, `Badge`...), `lucide-react` icons, UI copy in Spanish (the project's UI language; code comments follow the surrounding files), pages lazy-loaded as today, no new dependency, no env var. The button is hidden or disabled where it cannot work (no `navigator.mediaDevices`, no `MediaRecorder`, WebM unsupported) with a short explanation; on a 404 it shows that dictation is not enabled on this server and stops offering it for the session.
S10. Tests (Vitest + jsdom, red first where a runnable deterministic test exists): API service (method, raw Blob body, `Content-Type`, no multipart, error mapping incl. `status`), recorder hook (mocked `getUserMedia` / `MediaRecorder`: start, stop, 45 s cap, tracks stopped on error and unmount, size over 5 MiB rejected before upload), a pure draft-to-ticket helper (cart lines, caps, ambiguous/not-found handling, payment and cash rules), and the review modal (decisions, disabled Apply, never submits a sale). `npm run lint` stays at 0 warnings.
